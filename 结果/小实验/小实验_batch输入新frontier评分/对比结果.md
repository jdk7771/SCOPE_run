## 时间和 VLM 调用分析

详细核实见 `../../时间和VLM调用核实.md`。正式 baseline/fix split 1 有一次 01:11:34 的中断段，所以这里同时列完成段和 log 累计尝试时间。

| 方法 | 完成段耗时 | log 累计尝试时间 | 相对 baseline 完成段 | VLM 成功请求 | 全 log HTTP POST | 估算 API 响应总时长 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline/fix split 1 | **14:02:41** | 15:14:15 | - | **3,461** | 3,729 | **06:06:04** |
| batch reason1 | 17:21:19 | 17:21:19 | +3:18:38 | 4,841 | 4,844 | 08:10:19 |
| batch reason2 | 14:45:41 | 14:45:41 | +0:43:00 | 3,511 | **3,511** | 06:23:52 |

修正后的结论是：`batch reason2` 不能说比正式 baseline/fix split 1 少 911 次 VLM 成功请求；3,511 vs 3,461 反而多 50 次。若看全 log HTTP POST，reason2 比 baseline/fix 少 218 次，但 baseline/fix 的 3,729 包含中断段，不是完全公平的完成段对比。

因此，这个小实验更准确的价值是：修复 batch-local frontier ID 后，batch 解析稳定性显著变好；但相对正式 baseline/fix，它没有证明 VLM 成功请求数、运行时间或导航效果稳定优于 baseline。

## 结论

`batch reason2` 修复 batch-local frontier ID 后，batch 解析稳定性明显变好，VLM 成功请求数也明显低于 `batch reason1` 和旧 baseline pilot。

但它的导航核心指标没有超过 baseline/fix：Distance success 从 44.24% 降到 40.65%，Distance SPL 从 31.66% 降到 28.88%。所以这个分支适合保留为“减少请求/验证 batch scoring 可行性”的小实验，不作为主方法结果。
