对比对象：

| 方法 | 分支 | 结果目录 |

| 5 cm baseline/fix | `baseline/fix-tsdf05cm` | `01_基线_fix-tsdf05cm/原始结果文件/` |

## 实验目的

这个大实验回答的问题是：

在相同 GOAT-Bench split 1/2/3、相同 5 cm TSDF 条件下，加入 readable structured-BEV、Gaussian evidence BEV、米制 frontier 参数和结构化输出后，是否比非 BEV baseline 更好？

## 方法区别

`baseline/fix-tsdf05cm` 是当前公平 baseline：

- 使用 5 cm TSDF。
- 修复 stale snapshot object ID。
- 记录 VLM timing。
- 不给高层 VLM 额外输入 semantic BEV / Gaussian evidence BEV。

`feat/metric-frontier-readable-bev` 是当前主方法：

- 使用 5 cm TSDF。
- frontier 参数改成米制。
- 给高层 VLM 输入 semantic BEV 和 Gaussian evidence BEV。
- VLM 输出结构化 JSON，再映射回原 SCOPE 执行接口。

## 运行时间和 VLM 调用时间

时间这里必须分两个口径看，详细核实见 `../时间和VLM调用核实.md`。

| 方法 | split 1 完成段 | split 2 完成段 | split 3 完成段 | 完成段合计 | log 累计尝试合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| baseline/fix | 14:02:41 | 13:35:03 | 17:24:40 | 45:02:24 | 46:13:58 |
| metric readable-BEV | 20:09:44 | 20:35:10 | 06:29:45 | 47:14:39 | 69:27:35 |

如果只看最终完成段，readable-BEV 比 baseline/fix 多 2:12:15，平均每个 task 多约 9.8 秒。但这不是完整尝试成本：baseline/fix split 1 有 01:11:34 中断段；readable-BEV split 3 有 22:12:56 中断段，续跑时跳过 27 个已完成 scene。所以如果把同一 log 中中断后续跑也计入，readable-BEV 比 baseline/fix 多 23:13:37。

VLM 调用也要按日志末尾 summary 和全 log HTTP POST 分开看：

| 方法 | VLM 成功请求合计 | 全 log HTTP POST 合计 | API 响应总时长合计 | 说明 |
| --- | ---: | ---: | ---: | --- |
| baseline/fix | 11,330 | 11,598 | 19:44:16 | split 1 的 timing summary 不含前 01:11:34 中断段的 268 次 HTTP POST。 |
| metric readable-BEV | 11,778 | 16,868 | 25:22:19 | split 3 的 timing summary 只覆盖最后 06:29:45 完成段，不含前 22:12:56 中断段的大量请求。 |

因此，不能再用单个 `vlm_timing.json` 的 split 3 结果解释全部时间。更准确的结论是：readable-BEV 单次 VLM 请求更重，最终完成段耗时略高；如果把中断/续跑也算进去，主方法实际尝试成本明显更高。

## 结论

`feat/metric-frontier-readable-bev` 在 split 1/2/3 的四项核心指标上都高于 `baseline/fix-tsdf05cm`。合并后 Snapshot success 从 18.27% 到 **26.91%**，Distance success 从 39.88% 到 **48.02%**。

因此，这个分支可以作为当前最重要、验证最充分的主结果。它的代价是 VLM 输入更复杂，整体运行耗时更长。

## 不要过度解释的地方

这个实验验证的是一组改动的总效果，包括米制 frontier、readable BEV、Gaussian evidence BEV 和结构化输出协议。不能单独说提升只来自某一个单独模块。
